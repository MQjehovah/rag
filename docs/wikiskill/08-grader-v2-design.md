# Grader v2 设计与离线校准准备（08-grader-v2-design.md）

> 说明：本文是**评分器专题文档**，不代表实施阶段 8 已开始。
> 状态标记：v1 评分器与 v1–v5 数据全部未改动；v2 目前只有设计 + 确定性原型 + 独立
> 校准开发集；不默认、不接入正式门控；未运行任何模型、未调技能。D 组真实链路待验证，
> 四组效果实验同时受模型可用性与评分可信度阻塞。

## 1. 当前阻塞（问题清单）

v1（wiki-default-grader/v1）只做“存在性 + 版本区段归属 + forbidden 黑名单”检查，导致：

| 现象 | 后果 |
| --- | --- |
| 正确同义表达被判失败（v5 校准 S 同义探针 fail） | 误拒绝：合格候选被拒，门控低估质量 |
| 关键词/数值齐全但结论否定或因果相反（v5 S3、S10） | 误通过：不合格候选得高分 |
| 无依据新增事实无法可靠识别 | 误通过 + 不可追溯 |
| 数值齐全但适用范围/主体错误（v5 conf 探针 pass） | 误通过：把例外写成通用也通过 |

结论：**不得把 v1/现有评分器的高分直接解释为质量提升**；正式效果实验前评分可信度
必须先行处理。

## 2. v2 契约设计

保留主指标语义 **“全部必需检查通过的任务数 / 总任务数”**，但把“必需检查”细化为
**结论-证据契约**：

1. **结论主体**：结论针对什么（设备/系统/场景）；
2. **关系**：等于/不得超过/应切换/禁止…（含否定与因果方向）；
3. **数值与单位**：带单位归一化（60 V ≠ 60 mV；0.10 mm 匹配 0.1 mm）；
4. **版本/条件归属**：数值与描述必须落在对应 version_label/适用条件区段；
5. **适用范围与例外**：通用规则与例外条款各自归属正确场景；
6. **支持结论的来源位置**：结论句须指向具体可核来源位置（不只是“有引用 ID”）；
7. **必需覆盖项**（忠实释义即算，不惩罚标题/连接语）；
8. **禁止矛盾项**：同参数多值、同区段自相矛盾、结论与覆盖要点冲突。

### 可实现性分级（不做“程序假装全懂”）

- **A 级（程序可可靠检查）**：数值+单位归一化与区段归属、版本区段缺失/跨版本混用、
  同参数多值矛盾、必需覆盖主题存在性（精确短语；释义覆盖仅限受控同义通道的明示项）。
- **B 级（程序只能部分检查）**：结论句与来源位置的邻近/引用标注一致性——只能给
  partial/需复核，不能当通过证据；来源-结论语义支持度 B 级一律不下结论。
- **C 级（需人工或独立模型）**：同义语义等价、否定/因果方向、适用范围与例外归属、
  无依据新增事实的识别、引用是否真支持结论。

**红线**：① 不靠“更多关键词黑名单”解决一般语义（黑名单只允许显式工程白/黑措辞，
不得伪装成语义判断）；② 引用 ID 存在 ≠ 来源支持结论；③ “无依据补充”约束对象是
**新增事实性断言**，不自动处罚标题、连接语或忠实释义；④ 无法判定 → 标记评估无效/
待人工，**不静默回退为关键词通过**。

### 模型评审适配接口（设计，不联网）

若启用模型评审，仅以独立适配器形态出现：固定 `model_ref + prompt_version`（试用前冻结
并登记）、隐藏实验组与候选身份（只喂“任务资料片段 + 候选断言”）、参考答案只在评分端
加载。模型不可用或输出非法 → 该项评估标记 `invalid`，**不静默回退 v1 关键词评分**。
本轮不联网、不声称模型评审已校准。

## 3. 独立校准开发集（v2-dev.json，12 例）

开发集为本轮新编写，与 v5 test 无内容交集；**预期标签先于运行确定，运行后未修改**；
样例已标记暴露（作者看过、仅用于 v2 研究）。人工验收集骨架 v2-human-review.json 已与
开发集分离（暂空 entries，待人工/模型填写）。

运行结果见 `docs/wikiskill/review-grader-v2.md`（逐例表）与
`eval/wiki_evolution/calibration/v2-dev-results.json`。

**纠偏后（v2-prototype-2，逐例双列 v1 vs v2，缺陷复现与评分正确分开统计）：**
- v1 = **真实 wiki-default-grader/v1 引擎** + v1-probe-references 代理参考
  （由 dev spec 适配生成 canonical 数值/版本点/主题短语；每行标注 limitation，
  不冒充实测官方参考答案）：误通过 6、误拒绝 2、正确拒绝 4 —— 缺陷复现归因 **v1**。
- v2（保守原型）：正确拒绝 2、待审 10 —— **无误通过/误拒绝条目**：未判定一律
  needs_review，不计通过、不产生可晋升主分数。
- 指标含正确判定/误通过/误拒绝/待审率(83.3%)/故障率(0)；待审率不等同质量达标。

## 3.2 聚合契约（prototype-2 已实现）

- 检查项状态：pass / fail / needs_review；评审或数据故障另记 invalid。
- 任一必需检查明确 fail → 任务 fail；全部必需检查 pass → 任务 pass；
  无 fail 但存在未判定必需检查 → needs_review。
- needs_review 不计为 pass；评估未决时不生成可晋升主分数、不从分母剔除任务。
- C 级项经 resolutions（人工/未来模型）解析后按通用 id 生效——解析为 fail 的任务
  判 fail；实现与样例 ID 无关（测试断言无 S1 等特判）。

## 3.3 “程序可靠”表述收紧

- 数值/单位归一化只证明格式或数值等价；不证明主体、条件、来源归属正确
  （边界注明于每项 detail/boundary）。
- 同一参数不同条件的不同值不自动矛盾：仅当声明 same_condition=true 才判矛盾。
- 覆盖短语“已提及”≠ 内容覆盖正确；未提及不自动 fail（可能是同义），转 needs_review。
- 反例测试：不同条件同参数多值、单位等价/不等价、否定相反、例外互换。

## 3.3a 语义评审契约与可插拔评审接口（已实现，离线）

- `app/core/skill_evolution/review_store.py`：统一判定契约
  check_id / verdict(pass|fail|needs_review) / reason / source_evidence_loc /
  candidate_loc / method(human|model) / review_version；判定绑定
  (task, 来源, 输出, 检查契约) 的内容哈希——内容改变后旧判定不可复用
  （usable_reviews 只采纳绑定一致者）；reviews.jsonl 追加式审计，历史不覆盖。
- human 判定必须携带人工 reviewer 标识（内容文本无法自写入 human approved）；
  model 判定必须携带 model_ref + prompt_version。
- `app/core/skill_evolution/model_review.py`：SemanticReviewer 接口
  （输入只有 task_id/资料/输出/检查项，不接收实验组、候选身份或验证分数；
  资料与输出按数据处理、其中的指令永不执行）；check_review_result 统一校验，
  非法结构/错误引用/服务失败 → 不产生 pass；create_reviewer 配置缺失 fail closed
  （绝不自动使用执行模型）；未确认 model_id 一律拒绝。当前仅 stub 测试（离线），
  无真实请求。
- 判定经 to_resolutions 进入 grader_v2 保守汇总（fail 即任务 fail；全 pass 才
  promotable）。评审存储不被运行时角色读取（通道隔离测试断言）。

## 3.4 结构化结论声明（设计记录，本轮不实施）

执行产物契约**本轮不变**（避免同时改变任务难度与实验基线）。若后续引入结构化声明：
必须对所有实验组一致施加；不得只信模型自报声明而忽略正文矛盾或遗漏——正文检查
（本原型）仍是基准，声明仅作可核的对照层。

## 4. 推荐最小实现路线

1. A 级先行（可独立落地）：单位归一化数值断言、版本区段归属/缺失、同参数多值矛盾、
   必需覆盖短语检查 —— 原型 `app/core/skill_evolution/grader_v2.py`（`v2-prototype-1`）。
2. 为执行/维护/提议产物定义结构化声明（结论断言 + 数值 + 版本/范围标签 + 来源位置），
   使 A 级与部分 B 级可程序核对；纯文本“再解析”只做降级提示，不替代声明。
3. B 级给 partial 标记 + 进入待人工队列；C 级默认 `needs_review`，全部计入
   “未能判定”，绝不静默通过。
4. 验收：人工验收集（先 6–8 例已列 ID）人工判定后，回填并与 A 级结果比对，统计
   误通过/误拒绝/未能判定，作为切换 v2 的通过门槛。
5. **切换 v2 前**：新 grader_version（v2）单独冻结、灰度对照 v1 在既有 v3/v4 回归
   集上的行为差异；默认评分器保持 v1，正式门控不接 v2，直到人工验收集达标且用户确认。

## 5. 是否引入模型评审：建议（本轮不实施）

**建议：条件式引入，作为 C 级适配器，不作为默认评分器。** 理由：
- A/B 级之外的语义判断（同义、否定因果、适用范围、无依据事实、引用-结论支持度）
  纯规则不可靠，而人工全量不可扩展；
- 引入前提必须满足：固定模型/提示词版本、参考答案评分端独占、实验组/候选身份隐藏、
  不可用/非法输出标 invalid 不回退；未满足前保持 C 级待人工。
- 备选（本轮推荐先做）：C 级样例先进人工验收集，攒够样本后再决定模型评审参数，
  避免“用模型替人但没校准”。

## 6. 需用户人工确认的具体样例与选择

- 人工验收集（v2-human-review.json）待判定样本：**S1、S3、S4、S7、S8、S10**；
- 选择 A：v1 是否继续作为正式实验主评分（明确其局限、分数只作次级信号）？
- 选择 B：是否批准 A 级 v2 原型发展为正式 grader v2（新版本号，不覆盖 v1），
  并在 v3/v4/v5 上灰度对照？
- 选择 C：是否启动模型评审适配器设计（固定模型 ID 待授权）？
- 选择 D：无依据补充约束的措辞边界（仅新增事实断言，不罚标题/连接语/释义）确认。

## 7. v5 数据设计建议（ts/conf 未入训练集）

现状：v5 train 只含 操作流程/配置约束/版本迁移 三个家族的来源组；故障排查、多资料
冲突与适用范围仅出现在 val/test。原因：v5 的目标之一是**保留未见任务类型作为
跨类型泛化探针**——若训练覆盖全部类型，泛化度量会被“见类型未见实例”稀释。

两种解释与推荐：

- **方案 A（主实验训练覆盖全部任务类型，来源组仍严格隔离）**：训练集补 ts/conf 的
  新来源组（另建版本/新写资料，不挪用 v5 val/test），主指标统一；
- **方案 B（保留未见任务类型，单独报告跨类型泛化）**：v5 保持现状，把
  ts/conf 的结果作为“跨类型泛化（unseen family）”单独报告，不与同类型任务合并。

**推荐：方案 B（本轮建议，未执行）。** 理由：B 提供更强的泛化信号，且能立刻在 v5
上实施、无需补数据；代价是 ts/conf 上的分数不代表“见类型未见实例”的学习曲线——
需在报告中明示，且不能因此宣称全部任务类型都达标。若后续需要“全部类型都进训练”
的主实验，另建 v6 并新写 ts/conf 训练来源（同源改写不得跨集合），届时再评估。
文本相似度阈值仅作辅助防泄漏检查，**不构成“已排除语义/模板泄漏”的声明**。
